## 채널 설명 요약

아마존이 약 1년 사내 50개 일반 개발팀을 관찰. 같은 AI 코딩 어시스턴트를 써도 절반은 생산성 향상 3배 미만, 나머지 절반은 4.5배~10배 이상 배포 속도. 차이를 만든 것은 도구가 아니라 일하는 방식. 5습관: (1) 에이전트 컨텍스트 투자·모델 발전에 맞춘 가지치기 (2) 감속 후 가속 — 코드베이스를 에이전트 친화적으로 (3) 자율 실행 — 돌보지 말고 컨텍스트와 자가 검증을 넘기기 (4) 의도 명문화 — 사양·설계를 먼저 (5) 테스트 좌측 이동 — 로컬 결정론적 mock.

## 재구성 (en-orig)

### 4단계와 체감 (00:00)

Clare Liguori, AWS senior principal engineer, 주로 Kiro. 에이전트 AI 3년+. 산업 진화: inline completion → chat → vibe coding → **frontier development**(early adopter). 본인 체감은 이전 단계 전부 합쳐 **10–20%** 생산성. Amazon 파일럿은 **중앙값 4.5x**, 때로 **10x+**.

Frontier developer 3행동:
1. **hands-off coding** — 생산 코드의 **1–2%만** 사람이 씀. 나머지는 에이전트.
2. **드문 개입** — 코딩 어시스턴트가 **수 시간** 개입 없이 돌게.
3. **유휴 최소화** — 여러 에이전트를 **병렬**로 백로그에.

### 실험 1: Bedrock Mantle (02:12)

Bedrock(Claude·GPT 호스팅) 팀이 새 inference data plane이 필요. 추정 **30명 × 18개월**. 6명이 Kiro로 **76일**. 커밋 기준 최대 **20x**. Pathfinder. 한계: 회사 최상위 엔지니어, **distinguished engineer 2명** 포함. 분산시스템·LLM 아키텍처 전문가. 다른 팀에 재현 불가로 읽힘.

### 실험 2: Prime Video 10일 스프린트 (03:54)

다시 6명, Kiro. 전달 추정 **90주 → 24주**(10일 진척 기준). 다른 엔지니어 셋으로 Mantle에 가까운 성과. 한계: 온콜 없음, 회의 적음, 산만 최소화. 시니어가 **사전 3주** 동안 작고 잘 범위 잡힌 태스크+요구사항을 만들어 둠. 구조화된 한 시점이지 일상 아님.

### 실험 3: Amazon Stores 50팀 (05:38)

amazon.com·리테일 웹·오프라인 스토어. **평범한 50팀**(얼리/미드/시니어 혼재), **기존 시스템**(greenfield 아님). 작년 상당 기간 관찰. 지표는 커밋이 아니라 **프로덕션 배포 속도**. 절반 **<3x**, 다른 절반 **중앙값 4.5x·일부 10x+**. 90%가 Kiro 등 내부 도구 사용. 차이: step-function 팀은 **일하는 방식을 의도적으로 바꿈**. 나머지는 기존 방식 위에 도구를 뿌림.

인터뷰에서 **5습관**. "sprint 한 번"이 아니라 **매일**.

### 습관 1. 에이전트 컨텍스트 투자 (08:16)

머릿속 지식(슬랙, 온보딩, 코드리뷰, 스탠드업, 스프린트 플래닝)을 적어 skills/steering 파일로. 에이전트가 실수하거나 "나라면 안 그렇게 했을" 때마다: steering에 뭐가 빠졌나. 그리고 모델이 좋아지면 **do-not을 가지치기**. Sonnet 3.7 quirk용 금지는 Opus 4.5 이후 덜 필요. 새 습관: 아직 필요한가, 아니면 컨텍스트 팽창인가.

### 습관 2. 빨라지려면 먼저 늦춘다 (10:29)

인터뷰 거의 모든 팀이 채택 초기 **생산성이 내려갔다**. brownfield에서 에이전트가 성공하려면 코드베이스 일. 에러 메시지 개선, MCP 서버, 탐색 가능한 구조로 재배치. 일부는 언어 교체: 비타입 Python/JS는 컴파일 에러가 없어 모델이 추측. TypeScript·Amazon 내부에서 **Rust**(컴파일러 에러 메시지가 좋음). 필수는 아님.

### 습관 3. 돌보지 말고 먹이를 준다 (10:59)

하루 종일 대화형 vibe coding이면 루프에 사람이 묶여 **4–5x가 원리적으로 안 나옴**. 30초–1분 대기 → 병렬 불가. **먹이**: 할 일 + 자가 검증 방법. 에이전트는 품질 바(컴파일, 테스트 통과, 커버리지)에 닿을 때만 돌아옴. 그 내용을 steering에 넣어 매번 반복.

### 습관 4. 의도를 명시한다 (12:24)

Amazon은 spec-driven을 많이 쓰고 Kiro에 넣음. vibe coding: 높은 수준 프롬프트 → 코드 대량 생성 → "그게 아니야 / 요구가 틀렸어 / 그런 설계 아니었어". **의도가 틀린 코드**를 고치는 건 비생산적. 모호·복잡한 기능은 스펙 문서를 먼저(모델이 초안 써도 됨). 문서 왕복이 코드베이스에 흩어진 diff 왕복보다 싸다.

### 습관 5. 테스트를 왼쪽으로 (13:45)

빠른 피드백이 수 시간 자율 루프의 조건. 실수는 괜찮고, 신호가 있으면 스스로 고친다. 린터·유닛·통합·성능·보안 테스트 — 원래 해야 했던 위생인데 이제 ROI가 됨. 많이 보는 패턴: **로컬 결정론적 mock 서비스**. 라이브/클라우드 의존 통합 대신 노트북에서 루프. 피드백이 빠를수록 루프가 많고 에이전트가 생산적.

### 복병과 조직 (15:09)

습관 5개를 다 해도 nirvana 아님. early adopter. **번아웃**. ASR "FOMAT"(설명란 FOMO): 밤새 완벽한 프롬프트를 다듬어 아침에 패치가 있기를. 병렬 에이전트 → 터미널 탭 전환 인지 부하. AI 출력 리뷰가 작성보다 어려운 사람 있음 — 특히 주니어(시니어는 남의 코드 리뷰 근육이 있음).

조직이 프론티어 팀을 가능하게 해야 함.

1. **감속을 받아들일 것.** 리더가 "도구 있는데 왜 안 빨라" — 본인도 그런 적. 코드베이스·팀 습관에 **약 2개월** 투자. X에서 하루 20 PR 이야기에 매달 기능을 기대하면 안 됨.
2. **너무 넓게 너무 빨리.** Pathfinder·스프린트·50팀 파일럿에서 배운 것. Amazon의 2026 과제: 50팀 → **다음 2,000팀**. 성급 롤아웃은 맥락 없는 팀만 늘림.
3. **새 병목 = 의사결정 속도.** 예전 병목은 손코딩. 이제 코드가 **1–2개월**. 예전 9–12개월 제품이면 결정 2개월+런칭 승인 2개월이 묻혔는데, 지금은 그게 long pole. 프론티어 팀은 코드보다 결정에 시간을 더 씀. **되돌리기 쉬운 결정을 빠르게.**

한 줄: frontier engineering은 도구가 아니라 **일하는 방식을 의도적으로 바꾸는 것**. 루프에서 자신을 빼낼 것.
