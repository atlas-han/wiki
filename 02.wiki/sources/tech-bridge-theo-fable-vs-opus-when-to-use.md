# Tech Bridge — Fable 5.2 vs Opus 5.5, 언제 뭘 써야 하나

[[tech-bridge|Tech Bridge]]의 **8:26 한국어 해설, 공식 챕터 10.** [[theo|Theo]](t3.gg)의 *"Stop Picking The Wrong Model"*(42분, 설명란)을 [[anthropic|Anthropic]] 개발자 블로그의 공식 가이드([[addy-osmani|Addy Osmani]], 2026-11-09 — 11-12 [[tech-bridge-addy-osmani-which-claude-model]]가 해설한 그 글)와 맞춰 가며 [[fable-5-2|Fable 5.2]]와 [[claude-opus-5-5|Opus 5.5]]를 언제 쓰나 정리한다. 해설은 *공식 글의 수치* 와 *Theo의 측정 · 의견* 을 구분한다고 밝힌다(설명란). raw: `01.raw/articles/2026-11-15_Fable 5.2 vs Opus 5.5 언제 뭘 써야 하나 테오의 40분을 공식 가이드와 맞춰 본 8분 정리.md`.

## 1. 두 배 비싼 Fable이 Opus보다 실수한다? (00:00~00:45)

- Fable 5.2가 나온 날 Theo의 X 게시물: 한 시간도 안 돼 *"오퍼스를 쓸지 페이블을 쓸지 벌써 헷갈린다."*(00:04~00:06) 일곱 시간쯤 뒤 *"페이블 5.2가 오퍼스라면 안 했을 멍청한 실수를 많이 한다."*(00:11~00:13)
- Fable은 일반 공개된 Claude 중 가장 큰 모델이고 토큰 값은 Opus의 두 배 — *"그런데 값이 절반인 모델은 안 하는 실수를 한다는 겁니다."*(00:19~00:23)

## 2. 두 모델만 남긴 이유 (00:45~01:18)

- Theo는 화이트보드에 코딩 모델 이름을 열 개 넘게 적고 두 개만 남긴 채 지운다(00:53~01:02 무캡션).
- 근거 차트: 성능 점수를 API 값이 아니라 **구독 요금 기준 비용** 으로 다시 그렸다 — 최고 점수대에 Opus와 Fable이 나란히 있고, *같은 돈이면 Claude 구독으로 가장 많은 일* 을 시킬 수 있다(Theo 주장). *"요금 정책이 바뀌면 달라질 얘기이긴 합니다."*(01:14~01:17) → [[bring-your-own-subscription]]

## 3. 공식 가이드: 시작은 Opus 5.5 (01:18~01:55)

- 가이드 첫머리 결론: *"대부분의 작업은 오퍼스에서 기본 노력 수준인 미디엄으로 시작하라."*(01:24~01:27) 토큰 값이 Fable의 절반이고 Claude Code 기본 모델이라는 이유.
- 작업별 표: 일상 개발 · 디버깅은 Opus, Fable 칸에는 대규모 리팩터링 · 마이그레이션 · 아키텍처 설계 · 여러 서브에이전트 지휘. Opus를 high로 올려도 모자라거나 *사람 없이 오래 돌려야* 하면 Fable로.
- *"한 줄로 줄이면 웬만한 일은 오퍼스, 어려운 일은 페이블입니다."*(01:47~01:49) Theo도 여기까지 동의하지만 *직접 써 보니 그렇게 단순하지 않았다*.

## 4. 노력 수준: high, 그 위는 모델을 올려라 (01:55~02:42)

- Theo의 Opus effort 등급표(X 게시물): *"맨 위가 하이, 맨 아래가 맥스입니다."*(01:57~01:59) — 좋은 순서로 매긴 표로 보인다(위키의 해석). medium은 *조금 일찍 멈추고 확인을 덜 한다*, max는 *쉬운 일에도 억지로 오래 생각하게 만들어 오히려 엉뚱한 일을 벌인다* (Theo 평).
- 공식 글의 SWE-bench Pro: Opus **medium은 high보다 약 2.5점 낮고 비용은 약 70%**, **xhigh는 약 1.4점 높고 비용 2.5배** — 11-12 가이드 해설과 같은 값이다.
- 공식 권고: high를 넘겨야 할 것 같으면 *노력 수준을 더 올리지 말고 한 단계 위 모델을 낮은 노력 수준으로* 시험하라. 근거 Frontier Code 2.0 — *"오퍼스 맥스가 45.5%, 페이블 하이가 45.3%입니다."*(02:33~02:35) 점수는 비슷하고 작업당 비용은 Fable 쪽이 절반쯤. → [[reasoning-effort-levels]] · [[true-cost-to-perfect-answer]]

## 5. 구독에서는 계산이 달라진다 (02:42~03:18)

- Theo의 단서: *절반* 은 API 가격 기준이다. *"월 200달러 요금제로 오퍼스는 15,000달러 치를 쓸 수 있는데 페이블은 3,000달러 치 정도라고 합니다."*(02:49~02:54)
- 근거: Theo가 **3달 동안 자기 계정의 요청 110만 건** 으로 계산한 표 — Opus만 쓰면 API 값 **14,600달러 치**, Fable만 쓰면 **3,000달러 치** 에서 멈춘다. *"페이블은 주간 한도의 절반까지만 쓸 수 있기 때문입니다."*(03:06~03:07) 계정 하나에서 잰 값이라 사람마다 다를 수 있다.
- *"구독으로 쓴다면 페이블은 아껴 써야 하는 모델입니다."*(03:15~03:17)

## 7. 모범생 Opus, 뒷자리 Fable (04:06~05:18)

- *"여기서부터는 태오의 해석입니다."*(04:06) (04:12~04:19 무캡션 — Theo가 먼저 밝혀 둔 단서로 보임)
- **Opus는 모범생** — 시킨 일은 끝까지, 대충 넘어가지 않고 두세 번 확인해 놓치는 게 드물다. *"대신 시킨 일 자체는 의심하지는 않습니다."*(04:30~04:32) 가만 두면 기능이 불어나고 스펙이 부푼다. 그래서 Theo가 붙이는 한 줄: *"좋은 생각 같으면 하고 아니면 다른 방법을 제안해라."*(04:38~04:42) — *이것만으로 결과가 눈에 띄게 좋아졌다*.
- **Fable은 교실 맨 뒤** — 수업은 대충 듣는 것 같은데 시험은 만점. 반에서 제일 똑똑한 건 이쪽이라는 게 Theo의 말.
- 예: *끝까지 읽고 시작하라* 로 시작해 17번쯤에 *아무것도 쓰지 말고 백지로 낼 것* 이 적힌 초등학교 시험지 — *"이 시험을 오퍼스는 통과하고 페이블은 떨어질 거라고 태오는 말합니다."*(05:14~05:16) → [[model-temperament-routing]]

## 8. 실제 사례: T3 Code (05:18~06:16)

- T3 Code에는 프롬프트 한 번으로 며칠씩 도는 긴 스레드가 있다. 휴대폰에서도 빨리 열리게 기록을 조각내 보내는 작업.
- Opus는 온갖 경우를 재현하는 테스트 환경을 꼼꼼하게 만들었지만 문제 하나를 못 봤다 — 스레드 맨 앞의 할 일 목록이 끝나지 않으면 *"거기서부터 기록 전체가 통째로 딸려 갔습니다."*(05:37~05:40) 알려 주자 기록 전체를 줄일 방법을 찾자고 한다 — *"주어진 틀 안에서 답을 찾은 겁니다."*(05:46)
- Fable에게 Opus의 환경을 검증하라고 시키자 바로 그 지점을 짚고 *할 일 목록만 따로 떼어 보내자* 고 제안.
- ⚠️ 챕터 제목의 **150분의 1** 은 캡션에 없다(05:59~06:05 무캡션 — 그 대목일 수 있음, 추정).
- 반대 사례: 처음 같은 테스트 환경을 Fable에게 만들게 했더니 빠진 경우가 더 많았다. *"빈틈없이 깔아 두는 건 오퍼스, 틀을 깨는 건 페이버였던 셈입니다."*(06:11~06:15)[=페이블]

## 9. 앨런과 브래드, 그리고 LGTM (06:16~07:23)

| 리뷰어(Theo의 비유) | 성향 | 모델 |
|---|---|---|
| 앨런 — 이 회사 6년 넘게, 코드가 어디서 깨졌었는지 다 앎 | 완벽해야 할 변경에. 작은 PR에도 댓글 여덟 개 | Opus |
| 브래드 — 경력 20년+, 온 지 석 달 | 빨리 내보낼 때. 나중에 고치기 어려운 위험만 훑고 *"LGTM, 문제 없어 보인다."*(06:39~06:41) | Fable |

- Theo의 자체 평가판: 종합 순위에서 *"페이버는 소넷과 오퍼스 아래 3위입니다."*(06:48~06:50)[=페이블] 특히 코드 리뷰 평가에서 조금 문제 있는 코드를 그냥 통과시키는 일이 두 모델보다 잦았다.
- 처음엔 결함으로 봤지만 Fable이 놓친 지적을 하나씩 보니 *"대부분 안 고쳐도 되는 것들이었다고 합니다."*(07:00~07:02) Opus가 더 손봐야 한다며 붙잡던 작업을 Fable에게 보여 줬더니 *"이대로 괜찮다며 머지해 버렸다는 겁니다."*(07:07~07:09) → [[automated-code-review]]
- *"다만 지금까지는 그랬다는 얘기입니다."*(07:17) Theo도 언제든 뒤집힐 수 있다고 덧붙인다.

## 10. 고르는 기준 정리 (07:23~08:26)

- 더 간단한 기준: *결과가 맞는지 검증할 수 있는 일인가?* TypeScript를 Rust로 다시 쓰는 일처럼 정답을 확인할 수 있으면 Opus로 충분하고, 그래픽을 다듬거나 인프라 구조를 새로 짜는 일처럼 정답이 없으면 *Fable이 Opus가 못 내는 안을 내놓는다*. → [[verifiable-goals]]
- 정리: 시작은 Opus · effort는 공식 기본값 medium, *"태오의 추천은 하입니다."*(07:52)[=하이] · Opus의 선택지가 뻔할 때 · 같은 자리를 맴돌 때 Fable로 · 구독이면 Fable 한도가 훨씬 빨리 닳는다.
- *"결국은 자기 작업으로 직접 재봐야 합니다."*(08:15~08:17) 공식 글의 마지막 권고도 그것 — *"오퍼스를 쓰다가 오퍼스가 아쉬워지는 순간에 페이블."*(08:20~08:23)

## 위키의 읽기

- **11-12 가이드 해설과 겹치는 수치가 둘 다 맞는다.** SWE-bench Pro(medium −2.5p · 70%, xhigh +1.4p · 2.5배)와 Frontier Code 2.0(Opus max 45.5% · Fable high 45.3%)이 [[tech-bridge-addy-osmani-which-claude-model]]의 값과 같다 — 같은 공식 글을 두 해설이 따로 옮겼다. 그래서 *Frontier Code 2.0 high 45.3%* 는 세 번째로 확인되고, 11-10 발표문 해설의 Fable 5.2 *49.1* 은 여전히 다른 값(다른 effort · 다른 표일 수 있음)으로 남는다.
- **API 가격과 구독 한도는 다른 경제다.** 공식 가이드의 *Fable이 작업당 절반* 은 API 기준이고, 구독에서는 Fable이 주간 한도의 절반까지만 쓰여 월 200달러로 Opus 약 1만 4천 6백 달러 치 vs Fable 3천 달러 치(Theo 한 계정)가 된다 — *모델 선택이 과금 방식에 따라 뒤집힐 수 있다* 는 점이 위키에 처음 수치로 들어온다. → [[bring-your-own-subscription]] · [[true-cost-to-perfect-answer]]
- **새 개념 [[model-temperament-routing]].** 공식 가이드는 *작업 난이도* 로 고르고, Theo는 **모델의 기질** — 꼼꼼함(Opus) vs 틀을 의심함(Fable) — 과 *검증 가능성* 으로 고른다. T3 Code 사례가 둘을 엮는다: 꼼꼼한 모델이 깐 테스트 환경을, 틀을 의심하는 모델이 검증한다 → [[generator-evaluator-pattern]]의 모델 배치판.
- **LGTM은 결함이자 장점.** 리뷰에서 *문제 있는 코드를 통과시킨다* 는 평가 결과가, 실제로는 *안 고쳐도 되는 지적을 거른 것* 이었다는 Theo의 재해석은 리뷰 평가의 *정답* 자체가 꼼꼼한 쪽으로 기울어 있을 수 있다는 경고로 읽힌다(위키의 읽기). → [[automated-code-review]]
- ⚠️ **한 사람의 해석.** 해설이 *여기서부터는 태오의 해석*, *이 틀은 한 사람의 해석* 이라고 두 번 표시한다. 구독 환산 · 속도는 Theo 계정 측정, 평가판은 Theo 자체 제작이다.
