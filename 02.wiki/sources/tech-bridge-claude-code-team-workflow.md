# Tech Bridge — Claude Code 개발팀이 Claude Code를 쓰는 방법

[[tech-bridge|Tech Bridge]]가 한영자막을 입힌 22:23 대담. 화자는 [[anthropic|Anthropic]] Claude Code 팀의 [[thariq-shihipar]] · [[sid-bidasaria]] · [[robert-boyce]]. → [[2026-09-03_Claude Code 개발팀이 Claude Code를 쓰는 방법|raw 캡처]]

> ⚠️ **이름은 전부 채널 설명란에서 왔다.** 자막에는 이름이 거의 나오지 않아 **어느 발언이 누구의 것인지 확정할 수 없다.** 이 페이지는 화자를 특정하지 않고 "팀"으로 쓴다.

이 소스는 [[tech-bridge-claude-platform-agent-era]](같은 [[anthropic]] 팀의 다른 대담)와 짝을 이루면서 한 층 더 나아간다. 그쪽이 *"하네스는 while 루프다"* 라는 설계 관점이었다면, 여기는 **그 하네스를 만드는 사람들이 자기 하네스를 어떻게 쓰는가**에 대한 1인칭 증언이다.

## ① 도구 호출에서 목표 위임으로

대담 전체를 관통하는 전환이 초반에 요약된다.

> 우리가 예전에는 **녹취록(transcript)에 너무 신경을 쓰고, 개별 도구 호출이나 모델이 내리는 모든 결정에 신경**을 썼지만, 이제는 좀 더 넓은 시각으로 **"나는 목표가 있고, 이 목표를 달성하고 싶다"** 라고 생각하며 그 목표를 **모델에게 맡겨** 달성하게 된 것 같습니다.

수치가 붙는다 — **업무의 70~80%가 [[claude-tag|Claude Tag]]에서** 일어나고, 나머지 20%는 *"세부적인 부분을 수정하거나 Claude를 **세밀하게 관리**하고 싶을 때"* 다.

문제의 크기도 바뀌었다.

> **"이 클래스를 구현하세요" 또는 "이 함수를 작성하세요"와 같은 단순한 문제들과는 차원이 다릅니다. Claude Code 개발 초기 단계의 문제들이 바로 그런 종류였죠.**

→ [[goal-level-delegation]]

## ② Slack이 표면인 이유 — 맥락이 이미 거기 있다

> Claude Tag가 **"제품 컨텍스트는 뭐지?"와 같은 추가적인 맥락 정보를 찾아볼 수** 있기 때문이죠. 저희 팀이 이 제품이 어떤 모습이어야 하는지에 대해 내린 **모든 결정들**이, (…) **에이전트가 내리는 선택에 그 정보를 어떻게 통합해야 하는지 이해**하는 데 도움이 되어 의사 결정 과정을 훨씬 더 효율적으로 만들어 줍니다.

즉 Slack은 알림 채널이 아니라 **의사결정 아카이브**로 쓰인다. [[tech-bridge-ai-native-sdlc]]가 `intent.md`로 맥락을 **새로 만드는** 접근이라면, 여기는 **이미 쌓인 맥락이 있는 곳으로 에이전트를 옮기는** 접근이다. 같은 문제의 반대 방향 해법이다.

### 추상화 한 층 위 — 그리고 그 대가

> 지금 우리는 **Claude가 출력하는 실제 토큰보다 한 단계 높은 추상화 수준**에서 작업하고 있는 것과 같습니다. (…) 본질적으로 **내면의 독백은 Slack에서 여러분에게 보이지 않습니다.**

적응의 양가성이 솔직하다.

> **Claude가 생각하는 모든 것을 내가 직접 볼 수 있는 게 아니라는 걸** 깨달았죠. 하지만 **Claude가 언제, 무슨 말을 할지 스스로 선택한다는 점에서 정말 자유로워진 것 같기도** 해요.

전환의 조건도 명시된다 — *"**지금 모델들이 충분히 좋다**는 걸 알았어요. **녹취록을 자세히 검토할 필요 없이.**"*

## ③ 하네스 pruning — 이 소스의 가장 값진 부분

**todo 리스트의 생애가 사례다.** **Sonnet 3.5** 시절 모델은 *"다섯 가지 일을 시키면 **세 가지만 하고는 그냥 포기**"* 했고, todo 리스트가 그것을 고쳤다. *"그리고 정말 잘 됐어요."*

> 하지만 **1년 후에는 마치 사라진 것처럼 되어버렸죠. 이제 할 일 목록이 딱히 필요 없는 것처럼요.** 좀 더 **복잡한 메모리 상태** 같은 게 있고, 그런 것들을 믿고 의지할 수 있다는 거죠.

**여기서 하네스의 목적이 재정의된다.**

> 이러한 기능들을 하네스에 내장하는 것은 **현재 모델이 가지고 있는 몇 가지 오류 모드를 보완하기 위한 것**입니다. 그리고 모델이 더 좋아짐에 따라, 이제 우리는 **"이 모든 기능들은 더 이상 필요하지 않네요. 없애버릴 수 있겠어요."** 라고 말할 수 있는 **자유가 생겼습니다.**

교훈이 명시적이다 — *"**여러분이 만들어내는 것들에 대해 너무 집착하지 말아야 한다**는 걸 보여주는 완벽한 예시. 왜냐하면 그런 것들은 **꽤 빨리 사라질** 테니까요."*

→ [[harness-pruning]]

> 이것은 [[agent-harness-design]]과 [[harness-engineering]]에 **시간 축을 넣는다.** 기존 위키의 하네스 논의는 전부 *"무엇을 만들 것인가"* 였고, *"무엇을 언제 지울 것인가"* 는 비어 있었다. 그리고 [[self-harness]](하네스가 스스로 개선)와 방향이 반대다 — 여기서는 **모델의 향상이 하네스를 축소시킨다.**

지우기만 하는 건 아니고 균형추가 있다 — *"**작업 범위가 바뀌면서** 우리가 필요로 하는 도구들이 **다르게 보이기 시작**하는 것과 같습니다."*

**AskUserQuestion이 두 번째 사례다.** 설계에 *"정말 오랜 시간이 걸렸"* 고 호출시키기가 *"정말 어려웠"* 는데,

> 그러다가 최근에는 **그 도구를 거의 사용하지 않게 됐어요.** 제가 **아티팩트를 생성했는데, 그 아티팩트가 저에게 질문을 하더군요.** (…) **"이 도구는 전에는 겨우 하던 일을 이제는 할 수 있게 됐네"** 하는 느낌이었어요.

[[tech-bridge-multimodal-commerce-agent]]의 [[adaptive-response-format]]이 여기서 실측된다 — 질문을 던지는 **전용 도구**가 **형식을 스스로 고르는 아티팩트**에 밀렸다.

## ④ 2개월 주기 위에서 제품 만들기

> 제품의 기반이 되는 기술은 **항상 유효기간이 있다**는 거죠. 보통 **몇 년** 정도였는데 (…) AI 모델들은 마치 **2개월마다 근본적으로 바뀌는** 것 같고, **시간이 흐를수록 그 변화가 압축**되는 듯한 느낌도 듭니다.

긴장이 양쪽에서 온다 — **최첨단에 머물러야** 하고, 동시에 **오늘 쓰는 사람에게 가치를** 줘야 한다. *"**예술적인 면도 있고 과학적인 면도 있는데**, 어떻게 하면 제 **발밑에서** 너무나 빠르게 발전하는 이 기술에 맞춰 구축할 수 있을까."*

팀 구조가 여기서 따라 나온다 — *"**권한 시스템을 재작성**하고 결과물을 만드는 등의 작업을 **동시에 진행할 수 있는 소규모 팀**이 필요합니다."*

자기 위치에 대한 비유 — *"소프트웨어 개발이 나아갈 방향을 보여주는 **과장된 시간의 방**."* ⚠️ 자기 팀에 대한 서술이며 일반화의 근거는 제시되지 않는다.

## ⑤ 로컬 → 클라우드 → routine

경로가 아주 인간적인 일화에서 시작한다 — *"어느 순간 **집에 돌아가야** 했는데 (…) **'내 에이전트들이 더 이상 작동하지 않네.'**"*

추론이 한 줄로 압축된다.

> **로컬에서 실행되려면 클라우드에서 실행되어야 합니다.** 그리고 이제 클라우드에서 실행된다면 정말 흥미로운 일들을 할 수 있습니다.

그 "흥미로운 일"이 **routine**이다 — *"매일 우리가 받는 **모든 피드백을 살펴보고 중요도에 따라 분류**한 다음, 실제로 해결할 가능성이 높은 문제부터 해결."*

방향이 명명된다 — *"**세션 중에 모델에게 지시를 내리는 것에서 시작해서, 세션이라는 경계를 넘어** 한 단계 더 나아가"* 는 것. 이는 [[persistent-agent-teams]]와 [[dynamic-workflows]]가 각각 절반씩 다루던 것을 하나로 묶는다.

⚠️ *"생산성이 **10배**는 늘어난 것 같아요"* 는 개인 체감이고 측정 근거가 없다. 설정 비용도 함께 인정한다 — *"개발 환경에 대한 접근 권한을 부여해야 하는데, 그 **설정이 다소 번거롭기** 때문입니다."*

## ⑥ 코드 리뷰 — 사람이 무엇을 위해 남는가

기존 코드 리뷰의 사회적 기능에 대한 묘사가 정직해서 인상적이다.

> 누군가가 코드를 검토하고 **사소한 문제점 세 가지 정도만 골라서** 올리는 게 흔한 일이었던 것 같아요. 그건 마치, **내가 이 코드를 읽었다는 걸 너에게 알리는 신호** 같은 거였어.

그 층은 기계가 가져가고, 사람에게 남는 것이 정확히 규정된다.

> Claude가 **이 API 구조가 왜 이런 식으로 되어 있는지, 혹은 서비스 경계가 특정 위치에 설정된 이유가 무엇인지** 완전히 이해하지 못했을 수도 있다는 거죠.

즉 사람이 갖는 우위는 코드가 아니라 **결정의 역사**다. [[tech-bridge-grokbot-agent-teams]]의 "엔지니어=에이전트 매니저"와 같은 방향이지만, 여기서는 *무엇을 아는 사람으로 남는가*가 더 구체적이다.

효과는 주의의 재배치다 — *"Claude가 **인간 리뷰어들이 시간과 에너지를 어디에 집중해야 할지 선택**하는 데 큰 도움을 준다."*

## ⑦ workflows — fan-out, 적대적 검증, map-reduce

**기원이 코드 리뷰다.**

> 코드 리뷰가 **우리가 이렇게 큰 규모로 의견을 퍼뜨린 첫 번째 사례**였던 것 같아요. (…) 이렇게 **크게 펼쳐놓은 다음, 그것들을 하나로 합칩니다.** 이것이 바로 우리가 **test-time compute**라고 부르는 것이죠.

구조:

> Claude에게 나가서 **버그를 찾으라고 지시하는, 엄청나게 넓게 펼쳐지는(fan out) 시스템**을 가지고 있었어요. 그리고 **각 버그에 대해, 세 가지 다른 관점에서 버그를 살펴보고 실제로 버그가 존재하는지 확인하는 적대적 검토(adversarial review)** 를 수행할 수 있습니다.

목적은 찾는 것이 아니라 **거르는 것**이다 — *"**모든 버그를 걸러내고 사용자의 주의가 필요한 가장 중요한 버그만 남겨주는** 것."* → [[generator-evaluator-pattern]]

**그리고 fan-out의 진짜 문제를 짚는다.**

> 문제는 **정보가 부채처럼 퍼져나가면서, 그 방대한 정보를 다시 걸러내야 한다**는 점입니다. **마치 map-reduce 문제와 같아요.** (…) **전체 출력값을 다 읽어버리면 미쳐버릴 것 같거든요.**

이 위키의 [[dynamic-workflows]]·[[ultracode]]·[[managed-agents]]가 전부 fan-out 쪽(map)을 다뤘다면, **reduce가 병목이라는 지적은 새롭다.**

그리고 신뢰의 출처가 명시된다 — *"**자신감을 키우는 방법은 바로 test-time compute를 문제에 투입하는 것**입니다."*

### 에이전트가 자기 하네스를 짠다

> **Claude는 사실 자기만의 하네스를 만드는 데 정말 능숙하죠.** Claude가 이 **fan-out 구조가 어떤 모습이어야 하는지, 토폴로지가 어떻게 되어야 하는지, 한 에이전트의 출력을 다음 레벨로 어떻게 연결해야 하는지**를 파악하고 (…)

→ [[self-harness]] · [[dynamic-workflows]]

**그런데 신뢰의 근거가 뜻밖에 고전적이다.**

> 이것은 **결정론적인 코드 정의 동작과 에이전트 방식의 LLM 동작이 멋지게 혼합**된 것입니다. (…) 이 항목들을 순회하는 **for 루프**를 작성할 때 (…) **'아, 맞다. for 루프는 항목 중 하나라도 건너뛰지 않겠구나'** 라고 생각했다. 저는 그게 제 **신뢰도를 정말 크게 높여준다**고 생각해요.

에이전트가 **오케스트레이션을 코드로 물화**하는 순간, 그 층에는 결정론적 보증이 생긴다. [[tech-bridge-ai-native-sdlc]]가 lint를 *"예 또는 아니오, 이분법적"* 이라 부르며 결정론 층을 따로 세운 것과 같은 감각이다.

## ⑧ Claude Tag로 Claude Tag 만들기

> 제가 가장 집중해 온 부분은 **Claude Tag가 Claude Tag 자체를 개발하는 데 아무런 제약이 없도록** 하는 것입니다.

한 사례에서 루프 전체가 보인다 — 아이디어 → *"**누가 관심 있을지**"* 이해관계자 모으기 → 목업 → 구현 → 이벤트 계측 → 내부 배포 → **Claude Tag가 사용 현황을 모니터링** → *"**누군가 피드백을 남기면 저를 태그해** 주거든요."* 전부 Slack에서, *"**휴대폰으로도**"*.

**그리고 위임 수준이 한 번 더 올라가는 순간이 기록된다.**

> 처음에는 '**내 아이디어가 있으니 이걸 실행해 달라고 요청**해야겠다'라고 생각했지만, '잠깐, **Claude에게 퍼널을 개선해 달라고 요청**해 보자'라고 생각했습니다. (…) **좀 더 높은 차원에서 논의해 보고 싶습니다.**

기반은 검증이다 — *"Claude가 **PR을 생성하면, 테스트를 거쳐 결과물이 어떻게 보일지 스크린샷**을 보내줍니다. 그러면 어느 정도 확신을 가질 수 있게 되죠."* 피드백 소스 셋(**지표 · Slack · GitHub 이슈**)이 *"모두 Claude Code의 **기본 요소**"* 라고 정리된다.

## ⑨ 그리운 것 — 그리고 되찾은 것

**가장 어려운 것으로 꼽는 것이 기술이 아니다.**

> 요즘 소프트웨어 엔지니어에게 **가장 어려운 점은 바로 그런 사고방식의 자유로움을 유지하는 것** 같아요. (…) 그런데 우리가 어떻게 **한 발짝 물러나서 더 큰 그림을 생각**할 수 있을까요?

그리운 것 ① **성능 엔지니어링** — *"Claude가 **지금의 저보다 그 일을 훨씬 잘하는 것** 같아요. 하지만 저는 여전히 실제 성능 향상의 혜택을 누릴 수 있으니, 그건 좋은 일이죠."*

그리운 것 ② **세부에 파고드는 즐거움** — 개인 사이트의 **Mac OS X 10.4 Aqua 버튼**을 CSS 방사형 그라디언트로 재현하는 데 하루를 썼는데, 이제 *"Claude가 이제 다 해줄 수 있으니까 **내가 직접 수동으로 할 필요가 전혀 없다**."*

**그 상실이 곧바로 반대 방향의 이득으로 이어지는 대목이 이 대담에서 가장 좋다.** 일곱 살에 비디오 게임을 만들고 싶었지만 코딩을 몰라 **파워포인트**로 클릭 가능한 요소를 그렸던 기억을 꺼낸 뒤,

> 제가 어떤 아이디어를 떠올리든, **'아, 나한테는 기술적인 능력이 없어'라고 말할 필요가 없다**는 뜻이에요. (…) **소프트웨어 엔지니어링 분야 내의 모든 것이 이제 제 손이 닿는 곳에 있는 것처럼** 느껴져서 정말 신나요.

[[cognitive-offloading]]이 다루는 상실과 [[brain-hands-decoupling]]이 다루는 확장이 **같은 사람의 같은 문단**에서 나란히 나온 사례다.

마무리는 직업 자체에 대한 관점이다.

> **소프트웨어 엔지니어링은 변화의 직업** 같다는 생각이 들어요. (…) 근본적으로 소프트웨어 개발은 **이런 기술들을 활용해서 어떻게 놀라운 것을 만드는지**에 대한 것이라고 생각해요. (…) **서로 다른 문제를 해결하는 것 같지만, 어쨌든 문제 해결이라는 건 변함없는 거죠.**
