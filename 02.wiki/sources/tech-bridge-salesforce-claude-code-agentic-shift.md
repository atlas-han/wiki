# Tech Bridge — 사람이 못 찾은 버그, AI가 24시간 만에 (Salesforce 해설)

[[tech-bridge|Tech Bridge]]의 **6:44 한국어 해설, 공식 챕터 9.** [[salesforce|Salesforce]]가 엔지니어 1만 5천 명에게 [[claude-code|Claude Code]] 기반 에이전트 코딩을 퍼뜨린 1년을 정리한다. 거의 전부 내레이션이고, 영어 발췌는 두 곳(01:18~01:36 · 06:08~06:25)뿐이며 둘 다 화자가 발화되지 않는다. 근거는 설명란 *참고* 링크 — Claude 공식 채널 영상 *How Salesforce uses Claude Code*, Salesforce News 2026-05-27 · 2026-09-09 글 — 이고, **위키는 이 자료들을 열지 않았다.** raw: `01.raw/articles/2026-11-08_사람이 못 찾은 버그 AI가 24시간 만에 세일즈포스는 엔지니어 1만 5천 명에게 Claude Code를 어떻게 풀었나.md`.

## 1. 사람이 못 찾은 버그, AI는 24시간 만에 (00:00~00:46)

- *"사람이 몇 번을 파고 들어도 원인을 못 찾은 버그가 있었습니다."*(00:00~00:02) → *"디버그하고 고치고 컴파일하고 또 디버그하고. 그렇게 24시간 AI는 결국 원인을 찾아내고 수정안까지 내놨습니다."*(00:07~00:14)
- 이상한 결과: *"한두 달 만에 산출량은 두 배가 됐는데 버그까지 두 배가 되진 않았다는 거예요. 품질은 오히려 더 좋아졌고요."*(00:32~00:39)
- 00:17~00:26 무캡션(인트로 음악 추정).

## 2. 수십 년 된 코드를 몇 주 만에 — headless화 (00:46~01:43)

- 출발점: *"AI 에이전트가 일을 하려면 API가 필요한데 모든 기능에 API가 있는 건 아니었어요."*(00:51~00:56)
- 과제: *"모든 앱을 헤드리스 그러니까 화면 없이 API로 쓸 수 있게 바꾸는 일. 원래라면 6개월에서 1년짜리였죠."*(00:56~01:03) — *"그런데 이걸 몇 주 길어야 몇 달만에 해냈습니다."*(01:07~01:09)
- 영어 발췌(화자 미상, 해설은 *"엔트로픽이 공개한 소개문"* 이라 소개): *"80-90%of API coverage for all the clouds in a matter of less than a few months with no meetings across the teams."*(01:18~01:24) · *"imagine this is not new, this is preexisting code for decades to be able to go do that."*(01:30~01:36)
- ⚠️ 해설은 이 작업이 *"올해 드림포스에서 선보인 클로드 포스"*(01:38~01:40) 를 가능하게 했다고 한다. **영어 더빙은 같은 자리를 `Agentforce`로 말한다**(raw 헤더). 제품명을 확정하지 않는다.

## 3. 생산성은 무엇으로 잴까 — 유효 산출량 (01:43~02:23)

- 질문: *"AI 때문에 정말 나아진 건지 어떻게 증명하죠?"*(01:44~01:49)
- 줄 수의 함정: *"가장 쉬운 건 코드 줄수를 세는 거예요. 하지만 그러면 주석만 잔뜩 따라도 점수가 오르겠죠."*(01:51~01:55)
- ⭐ 처방: *"세일즈 포스는 스탠포드 연구진과 함께 유효 산출량이라는 점수를 만들었습니다."*(01:57~02:00) 주석 · 단순 수정은 낮게, 로직 변경 · 새로 만든 것은 높게 준다. *"커민마다[=커밋마다] 머신 러닝 모델이 시니어 엔지니어 패널처럼 코드를 검토해서 점수를 먹깁니다[=매깁니다]."*(02:08~02:12)
- 결과와 다음 단계: *"이 점수가 두 배로 뛰었습니다. 이제는 점수당 비용까지 따지면서 정말 효과가 있는지 확인하고 있고요."*(02:17~02:21)

## 4. 세일즈포스가 그린 지도 — 9단계 성숙도 곡선 (02:23~03:24)

- 문제: 도구를 다 나눠줬는데 *"다들 아주 단순한 일에만 AI를 쓰고 있었던 거예요."*(02:25~02:27)
- ⭐ *"에이전트 코딩 성숙도 곡선입니다. 아홉 단계네 개의 레벨론 단이죠[=아홉 단계, 네 개의 레벨로 된 거죠]."*(02:30~02:34) 대부분은 맨 왼쪽에서 시작한다.
- 곡선의 모양: 처음엔 신난다. *"그런데 곧 계곡이 나옵니다. 자신감이 떨어지는 구간이죠."*(02:41~02:45)
- 레벨 1: *"그냥 이거 해 줘라고만 말합니다. 어떤 결과가 좋은 건지는 알려주지 않고요. 짧은 일은 되는데 긴 일을 맡기면 무너집니다."*(02:45~02:52)
- 레벨 3: *"서브 에이전트 팀을 꾸리고이를 쪼개서 병률로[=병렬로] 돌리죠."*(02:58~03:02)
- 레벨 4: *"사람이 일일이 시키지 않아도 돌아가는 자유형입니다."*(03:04~03:06) 예: CI에서 테스트가 깨지면 에이전트가 고치고, 다른 에이전트가 리뷰하고 머지까지 한다(03:06~03:15).
- 결과: *"한두 달 만에 수많은 엔지니어를 레벨 3, 4로 끌어올렸고 지금 수천 명이이 자율 모드로 일합니다."*(03:15~03:22)
- ⚠️ **레벨 2와 아홉 단계 각각의 이름은 해설에 없다.** 곡선 그림은 화면에만 있고 보지 않았다.

## 5. 명령 대신 데모로 퍼뜨리기 (03:24~04:16)

- *"답은 의외로 단순했습니다. 영감 그리고 진짜 데이터."*(03:25~03:29) 사람들이 자기 문제를 라이브로 푸는 모습을 보여 주고, 실제 출시 제품으로 증명했다.
- 한 아키텍트: 남의 코드를 이해하려면 *"선너팀[=세 팀]과 얘기해야 해서 며칠씩 걸렸는데"*(03:38~03:40) 그 수고가 사라졌다.
- ⭐ 장애 대응 에이전트: *"이제는 팀마다 장애를 해결하는 에이전트가 있어요."*(03:44~03:46) 고친 건 바깥쪽 서비스 팀으로 갔는데 진짜 문제는 안쪽 서비스였다. *"에이전트가 원인을 찾고 담당 팀을 찾아서 그 팀을 직접 포출했습니다[=호출했습니다]."*(03:52~03:56)
- 스킬 유통: *"이렇게 만든 스킬들은 산내[=사내] 마켓플레이스에서 공유합니다."*(04:06~04:08) — 효과는 eval로: *"같은 작업을 스킬이 있을 때와 없을 때로 다시 돌려보면서요."*(04:11~04:13)

## 6. 코드 2배, 버그는? (04:16~04:53)

- *"지난 몇 달 동안 세일즈 포스의 코드형[=코드양]은 거의 두 배가 됐습니다."*(04:16~04:18) — *"코드당 버그는 오히려 줄었어요."*(04:23~04:25)
- 5월 Salesforce 글: *"PR은 늘었는데 전체 장애는 5% 줄었다고 적혀 있습니다."*(04:27~04:29)
- ⭐ 비결은 데이터: *"모든 티켓과 PR이 일관되게 라벨링돼 있어서 이걸로 벤치마크를 만들 수 있었죠."*(04:31~04:36) 새 모델이 나오면 이 벤치마크를 다시 돌려 더 나은지, 비용은 얼마인지 본다.
- ⭐ **실패 세트**: *"지금까지 모델들이 계속 실패해 온 작업만 모아둔 거죠. 새 모델이 이걸 통과하기 시작하면 그게 바로 모델을 바꿀 이유가 됩니다."*(04:44~04:51)

→ [[production-trace-eval-flywheel]](운영 데이터 → 벤치마크) · [[trusted-throughput]]

## 7. 검증 없는 자율은 자신감 연극 (04:53~05:21)

- 인터뷰 인용(해설 전달): *"검증 없는 자율은 자신감 연극일 뿐이다."*(04:54~04:56) — 영어 원문은 자막에 없다(en 더빙은 *theater of confidence*로 옮긴다).
- 리처드의 방식 ①: 일을 줄 때 좋은 결과와 나쁜 결과의 기준부터 정한다. 예: 새 스키마를 만들면서 *"기존 스키마를 건드리진 않았는지 다른 걸 망가뜨리진 않았는지"*(05:05~05:07).
- ⭐ 리처드의 방식 ②: *"에이전트에게 스스로 리뷰해라고 하지 않습니다. 대신 이렇게 말하죠. 증거를 보여줘."*(05:10~05:15) — *"찾은 특징들을 표로 만들고 그 증거를 보여 달라. 없으면 다시 해오라고요."*(05:15~05:20)

→ [[agent-change-evidence]] · [[verification-bottleneck]]

## 8. 다시 그 버그로 — 일에 맞는 모델 (05:21~06:09)

- 가장 큰 실수에 대한 답: *"일에 맞는 모델을 맞는 가격에 쓰는 것."*(05:26~05:28) — 평범한 파일 하나에 무거운 모델을 쓰는 사람들이 있었다.
- 원칙(9월 Salesforce 글이라고 전함): *"일상적인 일은 가벼운 모델로 가장 강력한 모델은 정말 어려운 문제에만"*(05:34~05:36). 24시간 버그는 *"길고 복잡한 일이라 큰 모델이 맞았던 겁니다."*(05:43~05:45)
- 그러나 리처드: *"찾는 것보다 검증이 더 중요하다고 말합니다."*(05:47~05:49) 고객의 재무에 영향을 주는 소프트웨어라서, 작은 버그를 고치다 찾기 힘든 큰 버그를 만들면 안 된다.
- 일의 크기: *"몇 분짜리 일은 그냥 대화로 끝내고 나머지는 큰 덩어리로 모아서 맡깁니다. 쪼개는 건 에이전트 팀이 합니다."*(05:58~06:04) 대신 처음 계획이 좋을수록 결과가 좋다.

## 이 위키에서의 좌표

- [[salesforce]]의 앞선 소스는 CEO의 무대 발언(09-23 [[tech-bridge-altman-benioff-dreamforce]])이었다. 이 편은 **회사의 엔지니어링 조직이 에이전트 코딩을 어떻게 들였는지**에 대한 첫 소스다(2차 전달).
- 같은 날 ingest한 [[tech-bridge-anthropic-code-review-seven-layers]]와 짝이다. Anthropic 편은 **만드는 회사가 자기 코드를 어떻게 리뷰하는가**, 이 편은 **큰 고객사가 어떻게 퍼뜨렸는가**이고, 둘 다 *코드는 두 배인데 사고는 늘지 않았다*는 같은 주장을 한다. 둘 다 당사자 자료다.
- *"스스로 리뷰해라" 대신 "증거를 보여줘"* 는 [[agent-change-evidence]] · 11-02 [[tech-bridge-ai-labs-claude-code-verification-review-loop]](Boris Cherny 간접 인용 *"give Claude a way to verify"*)와 같은 방향이다.
