## 진단 — 직무의 정의: 연구원이 아니다

소스는 직무를 **부정으로** 먼저 정의한다.

> **AI 엔지니어는 머신러닝 연구원이 아닙니다.** 연구원은 기초 모델을 처음부터 학습시키고, 논문을 내고, 깊은 수학과 석사 이상을 요구합니다. **AI 엔지니어는 이미 존재하는 모델을 사용해 구축합니다.** (01:15~01:45)

그리고 긍정으로 — **배선(wire)** 이라는 동사가 핵심이다.

> **그 모델을 가져다 유용한 작업을 수행하는 시스템에 배선하는 겁니다.** 데이터에 연결하고, 도구와 외부 정보에 접근을 주고, **메모리 루프와 가드레일**을 붙이고. (01:53~02:17)

이 위키가 지금까지 본 *AI 엔지니어* 는 **조직 이름**([[ai-engineer|AI Engineer]], 컨퍼런스 운영 조직)이거나 화자의 직함이었다. **직무 자체를 정의하는 소스는 이것이 처음**이다. 그리고 정의의 내용물 — 데이터 연결·도구·외부 정보·메모리·가드레일 — 은 이 위키가 [[agent-knowledge-sourcing]]·[[agent-memory]]·[[agent-governance-layers]]로 따로따로 쌓아 온 것들의 **직무 기술서 버전**이다. → [[ai-engineer-vs-ml-researcher]]

## 진단 2 — 어려운 것은 코드가 아니라 판단

> **AI 코딩 도구 덕분에 코드 생성이 쉬워졌으므로, 이제 어려운 부분은 코드 자체가 아니라 판단력입니다.** 애플리케이션을 어떻게 구조화할지, 무엇을 만들지, 왜 어떤 접근이 다른 접근보다 나은지. **수업에서 항상 배울 수 있는 건 아니지만, 직접 만들어 보면서 확실히 배울 수 있습니다.** (00:36~01:07)

[[taste-vs-judgment]]에 모인 여섯 입장은 전부 **이미 일하는 사람**(창업자·디자이너·엔지니어)의 말이었다. 이 소스는 **아직 진입하지 않은 사람**에게 같은 말을 한다 — 그리고 처방이 다르다. 저쪽은 *판단을 신호로 정의하라 / 슬롭을 측정하라 / 조향하라* 였고, 이쪽은 **"만들어 보라"** 다. 학위(*"꼭 필요한 것은 아닐 수도"*)와 수업(*"항상 배울 수 있는 건 아니다"*)을 밀어내고 **건설을 학습 경로로** 놓는다.

## 처방 — 세 층, 그리고 순서

| 층 | 내용 | 소스의 한 마디 |
|---|---|---|
| **1. 기초** | Python · Git · CLI · Linux · API | *"AI에만 국한된 것은 아니지만 이것 없이는 절대 만들 수 없다"* |
| **2. AI 특화** | 임베딩·벡터 검색 → **RAG 파이프라인** → **에이전트와 도구 사용** | *"현재 가장 수요가 많은 응용 AI 기술"* (에이전트) |
| **3. 출시·배포** | 컨테이너화·Kubernetes → **관측 가능성** → 모니터링(토큰 비용·보안) | *"노트북에서 나와 실제 사용자의 손에"* |

순서가 처방의 절반이다.

> **이 순서는 정말 중요합니다.** 사람들이 종종 하는 일은 **기초를 건너뛰고 데이터를 다루거나 인프라의 복잡성을 이해하기도 전에 바로 에이전트 구축이나 배포로 넘어가는 것**입니다. 그래서 **기본기를 다시 익히는 데 많은 시간을 보냅니다.** (02:37~03:01)

→ [[three-tier-ai-skill-stack]]

### 1층에서 눈에 띄는 것 — 읽기 유창성

> **Python 마법사가 될 필요는 없고, 코드를 읽고 여러분의 AI 에이전트가 쓰는 내용을 이해할 수 있을 정도로만 유창하면 됩니다.** (03:10~03:20)

**"쓸 수 있을 만큼"이 아니라 "에이전트가 쓴 것을 읽을 수 있을 만큼"** — 언어 학습의 목표가 **생산에서 검토로** 옮겨진 첫 진술이다. [[cognitive-offloading]]([[andrew-ng]]: 일을 시켜 버리면 학습이 손상된다)의 반대편에서 **어디까지 오프로드해도 되는가의 하한선**을 긋는다. → [[read-fluency-for-agent-output]]

그리고 API 층의 결론 문장이 이 위키의 [[agent-distributed-systems]]와 정확히 겹친다:

> **여러분이 궁극적으로 만들 모든 AI 제품과 솔루션은 근본적으로 애플리케이션에서 모델로, 도구와 서비스로, 그리고 되돌아오는 잘 구조화된 API 호출들입니다.** (04:29~04:41)

### 2층 ① RAG — 이 위키가 처음 받는 파이프라인 서술

> 문서들이 파이프라인으로 들어옵니다. **고정된 크기로 청킹**됩니다. **벡터로 임베딩되어 데이터베이스에 저장**됩니다. 질문이 오면 **검색한 관련 정보를 질문에 더해 둘 다 컨텍스트 창에** 넣습니다. **사실에 근거하면서도 자연어로 된** 결과를 얻습니다. (05:58~06:48)

[[retrieval-augmented-generation]] 페이지가 2026-09-08에 *"청킹·임베딩·재랭킹 등 구현 층위는 이 위키의 어느 소스도 다루지 않았다"* 고 적어 둔 빈칸을 **이 소스가 처음 채운다** — 재랭킹은 여전히 없다. 그리고 채택률 주장이 하나 붙는다: *"AI를 실험하는 거의 모든 회사는 어떤 형태로든 RAG를 원한다 — 임베딩을 쓰지 않더라도."*(06:48~07:00) ⚠️ 근거 없는 일반화.

벡터 검색의 정당화가 **의미 대 키워드**다 — *"Kubernetes라는 단어가 컨테이너나 오케스트레이션과 얼마나 유사한지"*. 2026-09-15 [[tech-bridge-graft-code-knowledge-graph|Graft 편]]이 **코드에서는 유사도가 방향을 모른다**([[reference-graph-vs-vector-search]])고 한 것과 나란히 두면, **이 소스의 예시는 전부 자연어 문서**(회사 정책·법률 문서·PDF)다. 두 소스는 모순이 아니라 **도메인이 다르다.**

### 2층 ② 에이전트 — 워크플로와의 구분

> **워크플로는 일반적으로 미리 정의된 경로를 따릅니다.** A단계, B단계, C단계. **에이전트는 다음에 무엇을 할지 동적으로 결정합니다.** 도구를 호출하고, 결과를 관찰하고, **루프를 돌며** 결정합니다. **이 루프를 안정적으로, 대규모로 만들 수 있는 사람이 좋은 AI 엔지니어입니다.** (07:23~07:53)

이 위키에 **워크플로 vs 에이전트**의 정의는 처음이다. [[dynamic-workflows]]가 *워크플로* 를 **에이전트들을 결정론적으로 조율하는 스크립트**로 쓰는 것과 **같은 축의 반대 끝**이고, [[agent-harness-design]]이 다루는 것이 바로 이 *루프를 안정적으로 만드는 일* 이다. → [[workflow-vs-agent]]

### 3층 — 관측 가능성이 신뢰의 조건

> 에이전트가 여러 데이터베이스를 오가며 데이터를 모으는 경우, **그 에이전트가 왜 그 최종 결정을 내렸는지 이해해야 합니다.** 그 모든 기능을 관찰할 수 있다는 것은 **AI에 대한 투명성과 신뢰**에 매우 중요합니다. (08:26~08:46)

[[agent-action-record]]가 *"에이전트의 말을 믿는 대신 무엇을 했는지 볼 수 있다"* 로 세운 것과 같은 자리를 **운영 층의 기술 요건**으로 다시 말한다. 모니터링 항목은 둘 — **토큰 비용**과 **보안**. 이 위키의 토큰 비용 논의([[file-discovery-tax]]·[[model-mixing-economics]])가 대부분 *개발 중* 비용이었는데 여기서는 **배포 후 비용**이다.
