# Tech Bridge — 저장소 38개를 에이전트 하나로? ‘홈 레포’ 패턴

[[tech-bridge|Tech Bridge]]의 **8:33 한국어 해설, 공식 챕터 9.** [[matt-pocock|Matt Pocock]]이 *"너무 뻔해서 올릴 생각도 안 했다"*(설명란)던 기법, **홈 레포(Home Repo) 패턴** — 집이 되는 저장소 하나에 [[agent-skills|스킬]] · AGENTS.md · 공유 문서 · 도구를 모으고, 다른 저장소는 **경로 한 줄**로 가리킨 뒤, 에이전트는 늘 그 저장소에서 실행한다. 해설은 그의 영상과 같은 날 올라온 aihero.dev 글을 기준으로 따라간다(설명란). raw: `01.raw/articles/2026-11-15_저장소 38개를 에이전트 하나로 홈 레포 패턴 Matt Pocock이 너무 뻔해서 안 올리려던 기법.md`.

테제(맺음):

> *"집이 되는 저장소를 하나 정합니다. 거기에 스킬과 설정은 모으고 다른 저장소는 경로 한 줄로 가리킵니다."*(08:01~08:07) *"에이전트는 늘 그 집에서 출발합니다."*(08:08)

## 1. 너무 뻔해서 안 올리려던 기법 (00:00~00:35)

- (00:00~00:08 무캡션) Pocock이 X에 올렸다 — *"아주 간단한 해법이 있다. 홈 레포다."*(00:09~00:11) 며칠 만에 조회수 28만 · 북마크 4,900개(해설 전달).
- 저장소 38개를 관리하는 수강생의 반응: 반신반의했는데 결과에 놀랐고 *"밤새 에이전트 용 문서를 썼다고 합니다."*(00:24~00:25)
- *"그런데 이 기법, 저장소 하나에 문서 몇 줄이 전부입니다."*(00:26~00:28)

## 2. 저장소가 여러 개면 생기는 일 (00:35~01:40)

- 스토어 프론트 · 결제 API · 관리자 대시보드, 가끔 보는 저장소 20개. 하나만 고칠 땐 그 안에서 에이전트를 돌리면 되고, 두 곳도 괜찮다 — 여러 폴더를 한 세션에서 다루고 PR은 저장소마다 따로.
- 문제는 *"스킬, 도구, 에이전트 MD처럼 세션마다 있어야 하는 것들은 어디에 둘까요?"*(00:54~00:58)
- 흔한 방법 ① **저장소마다 복사** — 어디서든 같은 스킬을 쓰지만 *"고칠 때마다 30개, 40개 저장소를 전부 맞춰야 합니다."*(01:05~01:07) 원문: 한 저장소에서 시작한 에이전트는 그 저장소만 보므로 복사본이 하나씩 생긴다.
- ② **각자 사용자 폴더** — 모든 저장소에서 보이지만 눈에 잘 안 띄어 갱신이 안 되고 *"팀 설정에서 점점 뒤처집니다."*(01:24~01:26) Pocock은 사용자 폴더를 *팀이 정한 방식이 아니라 내 작업 방식에 맞게 고치는 자리* 로 본다.

## 3. 홈 레포: 집을 하나 정한다 (01:40~02:35)

- 스킬 · 설정 파일 · 위키 · 직접 만든 도구를 전부 이 저장소 하나에 모으고, *"에이전트는 언제나 여기서 실행합니다."*(01:51~01:53) 원문 정의: 에이전트는 홈 레포에서 실행하고 다른 저장소는 *"필요할 때 열거나 클론합니다."*(02:03~02:05)
- 사용자 폴더와 다른 점 — *"홈 레포는 그냥 프로젝트입니다."*(02:08) 스킬이 git으로 버전 관리되고 팀이 함께 쓴다. 글은 사용자 폴더를 *그때까지 임시 방편* 이라 부른다.
- 함께 쓸 문서로 글이 첫손에 꼽는 건 **코딩 표준** — 한 벌만 있으면 프로젝트를 가리지 않는다.
- 장점 셋: 설정과 도구가 한 곳에 · 에이전트를 실행하는 자리가 하나로 · 여러 저장소에 걸친 변경을 한 세션에서.

## 4. 실제 홈 레포와 경로 한 줄 (02:35~03:57)

- 맨 위에 스킬 폴더(공개하지 않는 스킬), 설정 파일도 여기 — 버전 관리되니 *"고치면 그 설정이 조직 전체에 바로 퍼집니다."*(02:44~02:46)
- 저장소 목록은 CLAUDE.md 또는 AGENTS.md의 *Other repos*(판독 추정) 제목 아래 이름과 경로 한 줄씩. *"홈에서 다른 저장소로 가는 연결은 이게 전부입니다. 파일 안에 경로 한 줄."*(02:55~02:58) 어느 파일이냐는 도구마다 다르다 — 세션 시작 때 읽히는 파일(Claude Code는 CLAUDE.md).
- 새 컴퓨터에 그 경로가 없으면 에이전트가 클론해 오고, 있으면 바로 작업한다.
- 여러 에이전트가 같은 저장소를 건드리면 worktree를 나눈다 — 원문: *"저장소는 한 번만 클론하고 기능마다 그 안에 워크트리를 하나씩 만듭니다."*(03:22~03:26)
- 다른 방식: 저장소들을 홈 레포 **안에** 클론하고 `.gitignore`로 빼 둔다 — 38개 수강생의 방식.
- 저장소 추가는 한 줄, 필요하면 힌트 — *이 저장소는 고치기 전에 그쪽 AGENTS.md부터 읽어라*.
- 각 저장소에 남는 것: 그 저장소 전용 AGENTS.md · 빌드와 테스트 명령 · 전용 문서. 코드 · 이력 · 이슈 트래커는 제자리.

## 5. 저장소가 400개라면 — 규모별 처방 (03:57~04:47)

| 규모 | 처방(글 · 영상, 해설 전달) |
|---|---|
| 약 20개(영상은 30~40개도 가능할 것) | 저장소마다 포인터 한 줄 |
| 약 400개 | 포인터가 너무 많아 *"에이전트가 늘어날 결정이 너무 많아집니다."*(04:08~04:10) → **점진적 공개**(progressive disclosure): 저장소 대신 **영역별 파일** 을 가리킨다 — 결제 영역은 *빌링 파일을 보라* 고만 적고 그 영역의 저장소 목록은 그 파일 안에 |
| 수천 개 | 스킬을 쓰는 곳이 너무 많다 → *"스킬 마켓플레이스가 더 맞다고요."*(04:31~04:33) |

- git submodule도 5~10개면 괜찮다 — *"다만 포인터만으로 같은 일을 할 수 있다고 덧붙입니다."*(04:44~04:45)

## 6. 모노레포면 되지 않나 (04:47~05:24)

- (답의 앞부분 04:58~05:05 무캡션) *"늘 가능한 건 아닙니다."*(05:05) 공개 · 비공개 저장소가 섞여 있거나 팀이 모노레포를 받아들이지 않을 때. *"모노레포가 되면 모노레포를 쓰고 안 될 때 홈 리포가 그 자리를 대신합니다."*(05:12~05:16)

## 7. 위키와 도구 (05:24~06:38)

- 홈 레포를 쓰고 나서 *에이전트용 도구를 훨씬 과감하게 만들게 됐다*. 그는 홈 레포를 **퍼스널 위키** 라 부른다 — 사업의 중요한 자료를 마크다운으로 쌓은 큰 위키, *"본인 표현으로는 카파시 스타일의 LLM 위키입니다."*(05:37~05:39) 에이전트가 거기서 자료를 꺼내 강의 · 콘텐츠를 만든다. 위키를 만들고 최신으로 유지하는 법은 *다음 영상에서* → [[llm-wiki-pattern]]
- 도구: 위키 help 명령을 치면 Gmail · Slack · Discord · YouTube · GitHub · Google Calendar에 에이전트가 닿게 하는 명령 목록. 그래서 가능한 지시: *Discord에서 이 메시지를 찾아보고 crash course 저장소로 가서 고쳐라, 그다음 강의 영상 관리 도구의 스킬로 실제 강의까지 수정해라* — *"전부 한 세션에서요."*(06:07)
- 처음부터 도구가 필요하진 않다 — 글은 AGENTS.md의 포인터와 지금 쓰는 도구만으로 *시작하기에 충분하다* 고 한다. 공개 스킬 저장소(GitHub `mattpocock/skills`)도 홈 레포에서 포인터 한 줄로 연결.

## 8. 직접 만들어 보려면: 프롬프트 4단계 (06:38~07:47)

원문 글의 프롬프트를 저장소들이 모인 폴더에서 새 세션에 붙여 넣는다. *"에이전트는 계획을 승인받기 전에는 아무것도 바꾸지 않습니다."*(06:45~06:49)

| 단계 | 내용 |
|---|---|
| 1 | 저장소를 전부 찾아 목록을 만들고 어느 걸 홈 레포에 연결할지 묻는다 |
| 2 | 스킬 · 문서를 분류 — 여러 곳에서 쓰는 것 · 중복된 것 · 한 저장소 전용 · 설치해 쓰는 것 |
| 3 | 그 표로 계획을 합의 |
| 4 | 적용 — 공유할 것과 중복된 것만 홈 레포로 |

- 안전장치: *"승인 전에는 읽기만 한다."*(07:10) `.env` 같은 비밀 파일은 열지 않는다. *"커밋은 홈 레포에 하되 푸시는 사람이 결정한다."*(07:15~07:18) → [[no-silent-write]]
- 옮긴 자리 정리: 각 저장소에서 새 브랜치를 만들어 *홈으로 옮긴 복사본만* 지운다.
- 이슈는 에이전트가 모든 저장소의 트래커에 닿으니 *맞는 저장소에 올리게* 둔다. CI에서도 — 샌드박스에 홈 레포를 넣으면 필요한 저장소를 그때그때 클론. 팀이라면 *홈 레포가 곧 공유하는 대상* 이고 모두가 거기서 실행한다.

## 9. 감안할 점과 정리 (07:47~08:33)

- *"글과 영상은 매트 포콕 한 사람의 경험에서 나온 패턴이고 효과를 잰 수치는 없습니다."*(07:47~07:51) *"그는 에이전트 코딩 강의를 파는 사람이기도 합니다."*(07:54~07:55) 그리고 스스로 밝혔듯 저장소가 수백 개면 구조를 바꿔야 한다.

## 위키의 읽기

- **새 개념 [[home-repo-pattern]].** 위키는 스킬을 *어떻게 만들고 · 평가하고 · 배포하나* 를 [[agent-skills]] · [[mcp-skill-distribution]] · [[skill-evals]]로 갖고 있었지만, **멀티 레포 조직에서 스킬 · 설정이 *어디에 사는가*** 를 다룬 소스는 처음이다. 답의 핵심은 기술이 아니라 **실행 위치를 하나로 고정** 하는 것 — 그러면 설정 복사도, 사용자 폴더의 드리프트도 없어진다.
- **규모 사다리가 위키의 배포 줄기와 맞물린다.** 20개 포인터 → 400개 영역 파일(점진적 공개) → 수천 개 마켓플레이스. 마지막 칸이 [[mcp-skill-distribution]](원격 MCP로 스킬 배포)의 영역이다 — 홈 레포는 *팀 규모* 의 해법이고 조직 규모에선 배포 인프라로 넘어간다는 경계를 Pocock 쪽에서 긋는다. 400개 칸의 *영역 파일을 따라 들어간다* 는 [[deferred-tool-context]]의 점진적 공개와 같은 모양이다(위키의 연결).
- **이 위키 자체가 홈 레포의 한 형태다.** *Karpathy 스타일 LLM 위키* 를 홈 레포 안에 두고 에이전트가 거기서 출발한다는 구성은 [[llm-wiki-pattern]]의 *스키마 문서가 운영 규칙을 인코딩* 과 같은 축이다. Pocock은 위키를 *콘텐츠 생산의 원료* 로 쓴다는 점이 다르다(해설 전달).
- **안전장치는 위키의 *조용한 쓰기 금지* 와 같다.** 승인 전 읽기만 · 비밀 파일 금지 · 커밋은 하되 푸시는 사람 — [[no-silent-write]]의 실무판.
- ⚠️ **효과 수치 없음 · 판매자.** 해설이 스스로 두 번 짚는다. 38개 수강생의 반응도 Pocock 쪽 게시물에서 온 것이다.
