# 파일 vs 데이터베이스 — 에이전트 메모리의 저장 계층

**에이전트 메모리를 파일에 둘 것인가 DB에 둘 것인가의 논쟁에 대해, "둘 다 옳다 — 수명이 짧은 것은 파일에, 오래 남길 것은 DB로 승격하라"는 하이브리드 처방.** 파일은 모델의 본능에 맞고, DB는 파일에 없는 트랜잭션·백업·검색을 준다. 그리고 **git worktree는 파일에 트랜잭션이 없어서 쓰는 우회책**이라는 재해석이 붙는다. [[ignacio-martinez|Ignacio Martinez]]([[oracle|Oracle]]), [[tech-bridge-oracle-agent-memory-harness]].

> 딜레마 우리가 보유한 파일과 데이터베이스 **1월부터** (…) [파일 극대주의자, DB 극대주의자] (…) **둘 다 모든 것이 정확합니다**[둘 다 옳습니다]. (13:12~13:32)

> ⚠️ **화자는 DB 벤더다** — *"저는 포함시키지 않겠습니다만"*(13:22~13:26, 자기는 극대주의자가 아니라며) 뒤에 Oracle DBFS를 소개한다. 아래 비교표는 **화자의 표**이고, 파일 쪽 장점은 짧게, DB 쪽 장점은 길게 나열된다.

## 비교 (화자의 주장)

| | 파일 | 데이터베이스 |
|---|---|---|
| 모델 친화성 | ⭐ *"모델의 본능에 맞는다"*(en-orig 13:46), 만들기·삽입·추가가 쉽다, 비정형 | 정형(*"SQL을 떠올릴 때"*, 14:03~14:05) |
| 이식성 | POSIX 의미론 — Debian·Ubuntu 어디서나(14:25~14:30) | — |
| 동시 쓰기 | ❌ **트랜잭션 일관성 없음** — 8·16·32개 에이전트가 같은 파일을 동시에 수정할 수 없다(14:36~15:00) | ✅ ACID(16:21~16:33) |
| 검색 | 정규식 매칭 수준(16:46~16:48, ⚠️ 판독 보류 — 아래) | 하이브리드 검색·벡터 검색(15:41~15:50) |
| 내구성 | ❌ **백업 없음** — OS가 망가지면 전부 잃는다(15:50~15:57) | 복제·고가용성(16:33~16:38) |

> 이것들은 데이터베이스와 관련된 것들입니다. **그들은 30년이나 40년 전에 그 문제를 해결했고, 사람들은 그 사실을 다소 잊어버린 것 같습니다.** (16:00~16:05)

(en-orig는 *"354 years ago"* — ASR 오류. ko·en 변종의 *30~40년* 을 따른다.)

⚠️ 16:42~16:48 *"벡터 검색 기능도 있습니다. **파일에서는 아주 쉽습니다.** 오직 … 정규 표현식"* — **양 트랙 모두 "쉽다"** 인데 DB 장점 목록 한가운데다. 이 위키는 **"벡터 검색은 DB 쪽 장점"** 까지만 읽는다.

## ⭐ 워크트리 = 트랜잭션의 대용품

> 그렇다면 해결책은 무엇일까요? [트랜잭션] 일관성이 부족하기 때문에 (…) — **[워크트리]. [워크트리]. 예. 정확한.** 그래서 에이전트들이 원할 때 파일을 수정하지만 다른 에이전트 그는 지금 그 일을 처리하고 있을 뿐입니다. **다른 작업 트리를 생성합니다.** (…) 완료되면 (…) **메인 브랜치** (…) 이것 **[트랜잭션] 일관성이 없는 것을 피하는 방법입니다.** (15:02~15:36)

(청중이 답하고 화자가 복창한다 — **현장의 상식**이라는 뜻이다. ko는 둘 다 **"나무를 다루는 일"**.)

이 위키에서 worktree는 지금까지 **병렬 작업을 격리하는 도구**였다 — [[ai-native-sdlc]](*"일부가 병렬로 진행될 경우 worktree를 사용"*), [[agent-swarm]](Pstack의 *겁 없는 병렬성*). 이 소스는 같은 도구를 **저장 계층의 결함을 사람이 메우는 패턴**으로 다시 본다:

| 관점 | worktree가 해결하는 것 | 대가 |
|---|---|---|
| 병렬 작업 ([[ai-native-sdlc]] · [[agent-swarm]]) | 에이전트끼리 작업 공간이 부딪히지 않게 | 병합 |
| **저장 계층 (이 페이지)** | **동시 쓰기에 트랜잭션이 없다** | **머지 충돌 = 사후에 치르는 격리 비용** |

⚠️ **반론은 소스에 없다.** 워크트리·브랜치는 DB 트랜잭션에 없는 것을 준다 — **사람이 읽을 수 있는 diff, 리뷰, 브랜치 단위 롤백.** 코드처럼 *병합 전에 사람이 검토해야 하는* 산출물에서는 트랜잭션이 워크트리를 대체하지 못한다. 화자의 논지가 설득력 있는 곳은 **메모리처럼 리뷰 대상이 아닌 공유 상태**(카운터, 선호, 로그)다 — 화자가 예고한 실험도 *세 에이전트가 한 파일의 카운터를 올리는 경주*(16:54~17:13)였다. ⚠️ 그 **결과는 녹화에 없다.**

## 하이브리드 — 수명에 따라 승격한다

> **하이브리드 시스템이 더 효과적입니다.** (…) **단기 기억은 다음과 같은 곳에 존재합니다. 파일, 그리고 무언가가 필요할 때 장기 기억으로 승격되다 예를 들어, 사용자 선호도**, (…) [더 구조화된 공간인] 데이터베이스처럼 (17:46~18:07)

| 수명 | 예 | 자리 |
|---|---|---|
| 단기(휘발) | 코딩 에이전트의 to-do 목록(23:50~23:59) | 파일 |
| 장기 | 사용자 선호(18:00), 일화·절차 기억(24:03~24:54) | DB |

**승격(promotion)** 이 이 발표의 반복 동사다 — 메모리는 파일 → DB로, 워크플로는 대화 → 스킬로([[skill-self-improvement]]). **수명이 길어지는 것을 더 구조화된 저장소로 옮긴다**는 한 원리다.

Oracle의 답은 **DBFS**(데이터베이스 안의 파일 시스템) — *"데이터베이스 내에 파일을 저장합니다 (…) 트랜잭션 일관성을 가진 파일 (…) 벡터 검색 (…) 보안, 높은 이용 가능성"*(17:18~17:42). 즉 **파일 인터페이스(모델 쪽)와 DB 보장(운영 쪽)을 한 층에서.** ⚠️ 제품 주장이고 측정은 없다.

## 이 위키의 다른 저장소 논의와

- [[file-system-agent]](Vercel, 09-19) — **같은 출발점**(*파일은 모델이 가장 잘 다루는 인터페이스*), 다른 결론: Vercel은 **샌드박스에 파일을 붓고 끝**(읽기 위주, 단일 에이전트), 이 소스는 **여러 에이전트가 쓸 때** 파일이 깨진다는 데서 출발한다. **읽기 중심이면 파일, 동시 쓰기면 DB** 로 둘이 갈린다고 읽을 수 있다(⚠️ 위키의 읽기).
- [[corpus-as-filesystem-workspace]] — 검색 코퍼스를 파일 시스템으로 펼치는 쪽. 역시 읽기 중심.
- [[agent-distributed-systems]] — *메모리 = 캐시, 무효화가 문제*. 이 페이지는 **쓰기 일관성**을, 그 페이지는 **읽기의 신선도**를 다룬다. 둘 다 합쳐야 분산 저장소의 두 면이 된다.
- [[agent-memory]] — 무엇을 저장하나(내용·수명). 이 페이지는 **어디에**.

## ⚠️ 미해결

- **공유 메모리**(서브에이전트 ↔ 부모, 23:15~23:29)는 *"비교적 새롭다"* 고만 하고 **어디에 두는지 말하지 않는다** — 이 페이지의 논지가 가장 필요한 자리인데 비어 있다.
- **강등·삭제** — 승격만 있고, DB로 간 장기 기억이 틀렸을 때의 경로는 없다([[agent-memory]]의 Apex/Ivy 문제).
- 카운터 경주의 **실제 결과**, DBFS의 **성능·비용**.
- *"1월부터"* · *"지난 6개월"* — **어느 해인지 말하지 않는다.**
