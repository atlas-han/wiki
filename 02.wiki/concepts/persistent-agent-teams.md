# Persistent Agent Teams (지속형 에이전트 팀)

개인이 **정체성과 자기 컴퓨터를 가진 여러 봇**을 상시 보유하고, 코디네이터 봇을 통해 일을 배분하며, **동료에게 문자하듯** 소통하는 패턴. 세션 단위 코딩 하니스([[harness-engineering]]·[[agent-harness-design]])와 다른 축이다. 첫 소스는 [[cursor|Cursor]] [[grokbot|GrokBot]] 인터뷰 [[tech-bridge-grokbot-agent-teams]].

## 세션형 에이전트와 무엇이 다른가

| | 세션형 코딩 에이전트 | 지속형 에이전트 팀 |
|---|---|---|
| 수명 | 대화·태스크 단위 | **상시**. 사용자가 자리에 없어도 실행 |
| 정체성 | 없음 (도구) | 이름·아바타·성격 |
| 실행 환경 | 사용자의 머신·세션 | **자체 컴퓨터**, 사용자 도구에 로그인 |
| 조직 | 사용자가 직접 지시 | **코디네이터 봇**이 배분·추적 |
| 인터페이스 | 조절 장치 많은 전문가 UI | 메시징 (동료 은유) |
| 사용자층 | 파워 개발자 | 역할 무관 |

## 네 개의 구성 요소

1. **정체성** — 이름·아바타·성격. 사소해 보이지만 대중 채택의 실제 동인으로 지목된다.
2. **자체 컴퓨터** — 지속성의 근원. *"컴퓨터 앞에 있지 않아도 실행됩니다."*
3. **코디네이터 계층** — 비서실장(chief of staff) 봇이 일정을 알고 다른 봇에게 임무를 보내고 진행을 확인한다. 사람은 팀장이 아니라 **팀장의 상급자** 자리로 한 칸 더 올라간다.
4. **메시징 UI** — 힘과 복잡성의 균형에서 단순함을 택한 결과.

> 동료를 일일이 간섭하면서 "지금 어떤 툴을 사용하고 있나요?"라고 물어볼 필요는 없잖아요. 하지만 당신은 그것을 사람처럼 대하고 싶어 하잖아요.

## 엔지니어의 역할이 둘로 갈라진다

이 패턴의 가장 중요한 귀결. [[lauren-tan]]:

> 에이전트를 관리하는 엔지니어링 매니저와 같은 역할을 하게 되는 거라고 생각합니다. 하지만 엔지니어로서 우리의 중요한 책임 중 하나는 ... **코드베이스를 좋은 상태로 유지**하는 것이라고 생각합니다.

- **위로 — 에이전트 매니저**: 여러 봇과 협업하다 한 발 물러나 관리. 미슐랭 주방 비유에서 **수석 셰프의 품질 관리**.
- **아래로 — 환경 관리인**: 에이전트가 성공할 수 있는 코드베이스를 만드는 일.
  - 에이전트가 작동하도록 **리팩토링·재작성에 투자**
  - 규칙·스타일 가이드를 **린트 규칙과 CI 실패로 인코딩** — 부탁이 아니라 기계가 거부하는 형태

두 번째가 [[verifiable-goals]]·[[llm-coding-guidelines]]의 정확한 재확인이다. *"에이전트가 항상 똑똑한 것은 아니"* 라는 전제에서 출발한다.

## 대중화의 장벽은 모델이 아니라 UX

> 실제 인프라와 일상적인 작업에 에이전트를 활용하기 위한 UX가 형편없기 때문에 여전히 대부분 코딩 기반 에이전트 사용이 이루어지고 있습니다.

에이전트가 코딩에 몰려 있는 것은 코딩이 유일한 적합 영역이어서가 아니라, **비개발자용 인터페이스와 인프라가 없어서**라는 진단. 채택 테스트는 벤치마크가 아니라 *"내 어머니가 쓸 수 있는가"* 로 제시된다.

## 가격이 곧 병렬성

패턴의 경제적 전제 조건. [[grok-4-6|Grok 4.6]]은 Cursor Bench 3.2에서 **70.8% @ $2.81/task**, Fable 5 Max는 **70.5% @ $17.32** — 동등 점수대에서 약 6배 저렴.

1인이 봇 팀을 상시 유지하는 그림은 **작업당 비용이 한 자릿수 달러여야 성립한다.** 효율성 벤치마크와 "각자 봇 팀을 갖는다"는 비전은 같은 주장의 두 얼굴이다.

> 20달러의 예산이 있는데 작업당 비용이 낮아지면 더 많은 작업을 처리할 수 있는 것과 같습니다.

## 위키 내 대비

- [[agent-org-adoption]] — 채택 경로(**내부 PMF → 외부 출시**)는 같은 문법. 다른 점은 확산이 엔지니어링 **밖**까지 갔다는 것.
- [[frontier-engineering]] · [[tech-bridge-dhh-agent-productivity]] — 엔지니어 역할 이동에 대한 세 번째 독립 증언. 다만 **병목의 위치**가 서로 다르다: [[dhh]]는 아이디어·taste, [[roshan-sadanani]]는 아이디어→제품 **변환**. 세 소스 모두 코드 작성 자체는 병목에서 내려놓았다.
- [[self-harness]] — GrokBot의 상당 부분이 GrokBot으로 만들어졌다는 자기 참조 루프. self-harness가 *하니스*를 자기 트레이스로 개선한다면, 여기서는 *제품*이 자기를 만드는 노동력이 된다.

## 열린 질문

- ⚠️ 벤더 인터뷰라 생산성·벤치마크 주장에 독립 검증이 없다.
- 봇이 사용자의 모든 도구에 로그인한 채 상주하는 모델의 권한·감사 경계를 소스는 다루지 않는다. [[prompt-injection]]이 걸리는 자리이지만 언급되지 않았다.
- 코디네이터 봇이 배분한 일의 실패가 어디서 잡히는지 — PR 리뷰가 유일한 게이트로 보인다.

## 코디네이터 없는 1인 버전 (2026-09-02)

[[ivanna-kacevica|Ivanna Kaceviča]]([[tech-bridge-flutter-ai-workflow]])의 워크플로는 이 패턴의 **개인 개발자판**이다.

> 저는 세 대의 병렬 기계를 사용합니다. 한 대는 Claude를 실행하고, 한 대는 Codex를 실행하고, 한 대는 Antigravity를 실행합니다. 그리고 그들은 **서로에게 업무를 인계**합니다.

| 구성 요소 | GrokBot | Kaceviča |
|---|---|---|
| 정체성 | 이름·아바타 | 없음 (도구 셋) |
| 자체 컴퓨터 | 봇마다 | **기계 세 대** — 있음 |
| 코디네이터 | 비서실장 봇 | **사람** — 인계를 직접 한다 |
| 인터페이스 | 메시징 | 각 도구의 세션 |
| 목적 | 역할 무관 대중화 | 저녁·주말 사이드 프로젝트(RevenueCat Shipaton) |

즉 네 구성 요소 중 **자체 컴퓨터**만 갖춘 상태다. 그래도 *"풀타임 본업 뒤에 에이전트 팀을 운영한다"*는 서술은 이 패턴이 제품 없이도 파워 유저에게서 먼저 자생한다는 신호이고, 위 "대중화의 장벽은 UX" 진단과 맞는다 — 코디네이터를 사람이 하는 한 이 형태는 파워 유저 밖으로 나가지 못한다.
