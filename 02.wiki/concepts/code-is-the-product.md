# 코드가 곧 제품이다

**사용자가 코드·API·문서·아키텍처를 직접 읽는 조직에서는 코드 품질이 곧 제품 품질이다.** 따라서 **"내부 품질"과 "사용자 경험"을 나누는 흔한 구분이 성립하지 않는다.**

> 우리에게는 **코드가 곧 제품**입니다. 사람들이 **코드를 내려받고, 코드 위에 쌓고, 우리 API와 상호작용하고, 문서를 읽고, 아키텍처 위에 만듭니다.** 따라서 **코드 품질이나 우리가 배포하는 SDK 품질에서의 게으름은 곧바로 더 나쁜 개발자 경험으로 번역**되고, 사람들은 **화가 나거나, 사업이 멈추거나, 제품을 꺼 버립니다.** — [[tech-bridge-ambitious-software-agent-era]] (12:51~13:15)

## 대조 — 소스가 직접 갈라 놓는다

같은 발표가 **다른 종류의 소프트웨어**를 먼저 열거한다([[ambitious-software]]):

| 종류 | 코드 품질의 위치 |
|---|---|
| **연구** | *"코드 품질이 가장 중요한 게 아닐 수 있습니다"* |
| **프로토타입** | *"빠르게 반복하고 빨리 움직이는 게 중요합니다"* |
| **애플리케이션** | *"사람들이 내부 코드를 보지 않습니다. **바깥에서 어떻게 보이는지만** 봅니다"* |
| **라이브러리·SDK·프레임워크** | **코드 자체가 표면이다** |

**이 구분이 에이전트 도입 판단을 가른다.** 앞의 셋에서는 [[slop-cannon|슬롭 캐논]]의 비용이 낮지만, 마지막에서는 **머지되지 않은 수만 줄이 곧 낭비**다.

## 그래서 무엇을 에이전트에게 맡겼는가

역설적으로 **가장 지루한 일**이다.

> **대담한 프로젝트에서 코딩 에이전트의 덜 섹시한 용도는 사실 극도로 평범한 작업을 하는 것**입니다. (12:02~12:09)

소스가 드는 목록:
- **릴리스 체크리스트 검증**
- **안정 릴리스로의 버그 수정 백포팅**
- **문서 동기화** — *"모든 것에 예제가 있는지, 문서가 말하는 대로 실제로 그것을 문서화하고 있는지"*

문서 항목의 근거가 [[comments]](리팩터링 code smell)와 정확히 맞물린다:

> 인간은 **코드는 고치고 주석은 안 고칩니다. 그래서 시간이 지나면 주석 상당수가 낡고 상황이 아주 헷갈려집니다.** (13:43~13:50)

**이 위키가 code smell로 분류하던 것이 "에이전트에게 넘길 수 있는 유지 작업"으로 재배치된다.**

## 결과 주장

**주 1회 혹은 주 여러 번 릴리스** — *"예전 같으면 그렇게 자주 릴리스하기가 두려웠을 것"*.

⚠️ **패치 릴리스 수는 슬라이드에 있고 자막에 값이 없다.** 팀 규모(**핵심 엔지니어 3명**)만 확인된다.

## 같은 조건의 다른 쪽 — PR을 받는 자리

**코드가 제품이면 기여도 제품에 직접 닿는다.**

> **모르는 사람들에게서 아주 많은 PR을 받습니다. 그리고 모든 PR이 똑같이 만들어지지는 않습니다. 사용자들이 모델에게 자기 의도를 전달하는 데 꽤 서툽니다. 기여자들은 코드베이스가 어떻게 진화해야 하는지를 깊이 생각하지 않습니다. 그냥 자기 버그 수정이나 기능이 들어가기를 바랄 뿐이고, 많은 해법이 억지로 끼워 붙여져 있습니다.** (17:06~17:28)

그래서 **모든 PR을 한 줄 한 줄 사람이 읽는다.** AI 리뷰는 **선행 필터**로만 쓴다.

→ **이 위키에서 [[agent-org-adoption]]의 수용(receiving) 측이 처음 기록되는 자리**다. 09-12 [[lauren-tan]]이 *한 달에 PR 1,000건을 내는 쪽* 이라면 이쪽은 **그것을 받는 쪽**이다.
